# 全体像

Excel を正本にしている現在の形です（スプレッドシートへの移行は README の「移行中のこと」）。

```
販売管理システム（公開APIなし）
        │  monthly_run.py ingest が月1回、前月分を取得（毎月2日 06:00 に定時実行）
        ▼
   売上TSV（号機×日付×検量区分）
        ▼
   Excelブック  ← 唯一の正
   ├ 取込_夜間 / 取込_回収時          取得した明細
   ├ M_号機 / M_契約 / M_カレンダー   マスタ（人が直す）
   ├ 入力_月次調整                    手入力（消してはいけない）
   ├ 入力_その他売上                  入力用スプシから import-other で取り込む
   ├ 集計_月次                        号機ID結合で自動
   ├ 請求_<支払先>                    支払先ごとの請求書シート
   └ 発行台帳                          発行の記録
        │  verify_workbook.py（ここで止まりうる）
        ▼
   請求書PDF（ドラフト）→ 人が確認して発行

入力用スプシ（EC・催事・卸を人が入れる）
        │  import-other：閲覧専用のサービスアカウントで Sheets API から読む
        ▼
   入力_その他売上（対象月の行だけ置き換え）
```

定時実行に載っているのは `ingest` だけです。請求額の確認通知（`remind`）は現在は手動実行で、定時実行への切り替えを予定しています。`draft` は人が手で流します。

これとは別に、毎晩1回、号機ごとの補充後の販売本数をVMSから取り、チャットに通知する定時ジョブがあります。

## 設計上の要点

### ブックは1個をずっと使う

作り直しません。`build_workbook.py` は初回の型作り専用で、運用中に走らせると
手入力シート（月次調整・その他売上・発行台帳）が消えます。

**定数ではなくシートが正。** 契約条件は Python の `CONTRACTS` ではなく `M_契約` シートが正本です。
コード側の定数は初期構築時の種でしかありません。運用者がコードを触らずに条件を変えられることを
優先しました。支払先を1社増やすときもブックの作り直しは不要で、マスタに1行足して
予備の請求書シートを使います。

### 号機IDで結合する

販売管理システム側で機器の表示名が変わることがあります。名前で結合すると、
改名された瞬間に集計から静かに消えます。すべての数式は**号機ID**で結んであり、
表示名はマスタのB列を直すだけで追従します。

同じ1台が最大4通りの名前で呼ばれていました（システム上の機名／旧管理表の通称／
決済端末側の登録名／実際の設置場所）。名寄せは端末シリアルを軸にしています。

### 数式はスプレッドシートにもある関数に限る

数式は Excel 専用関数を使わず、Google スプレッドシートにもある関数だけで組んでいます。
`verify_workbook.py` がこれをチェックします。

ただし、**正本の xlsx をスプレッドシートで開いて保存することは禁止**しています。
一度そうして保存されたファイルでは、整数が小数になる、セルのロックや入力規則が外れる、
数式が配列数式に変わる、といった崩れが起きました。スプレッドシートを正本にするなら、
xlsx を取り込むのではなく、スプレッドシート側を作り直す方針です（移行の作業はこの方針で進めています）。

### 何度流しても同じ結果になる

`ingest` は同じ月を2回流しても二重登録しません。`import-other` も対象月の行だけを置き換えるので、
失敗したらそのまま流し直せます。

発行日は**PDFを作った日**です（運用側の判断で「作成当日」に決まりました）。
過去分を出し直すときは、控えと合わせて実際の発行日をマスタに入れます。

### 検量区分という罠

売上には「夜間集計」と「回収時検量」の2系統があり、基準日が違います。
販売日は夕方基準で更新され、回収時検量は回収日ベース。そのため
**月末月初の売上は隣の月に寄ります**。請求は回収時検量（回収した現金の実額）を正にしています。

月次では割り切り、年1回ほど通期で突き合わせる運用にしました。決済端末側システムとの
突合では3ヶ月で数千円規模のズレが出ています。これは不具合ではなく基準日の違いによるもので、
そう記録してあります。

### 止まる仕組みを先に作る

請求書は金銭が動きます。`draft` は必ず `verify_workbook.py` を通し、
問題があれば**PDFを出さずに通知して終了コード1**を返します。

出力はあくまでドラフト（未承認）で、人が中身を見て承認してから発行します。
自動化したのは作業であって、承認ではありません。

### 焼き付けと再計算のずれ

算定根拠の明細は行数が月ごとに変わるため数式にできず、出力時に値を焼き付けています。
対象年月を切り替えると明細だけ古いまま残るので、警告行を出しています。
**PDFが正、ブックは作業場**という整理にしました。
