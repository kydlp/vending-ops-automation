# 契約条件のモデル化

自販機は設置場所ごとにオーナーが違い、契約条件が1社ずつ違います。
この案件では8台に対して、請求書・支払明細を出す相手が10社ありました。同じ支払先が複数台を持つことも、
1台に複数の契約がぶら下がることもありました。

## 方式は2つ、修飾が4つ

| 方式 | 計算 | 出す書類 |
|---|---|---|
| **料率** | 支払額 = 売上 × 料率 | 支払明細書（当社が設置手数料を払う） |
| **現金渡し** | 請求額 = 回収現金 − 日額 × 稼働日数 − 月額固定 − 金額の調整 | 請求書（回収現金から先方の取り分を差し引いた額を請求する。キャッシュレス分は当社が受け取る） |

これに修飾が乗ります。

**最低保証。** 料率方式で、算出額がこの額を下回ったらこの額を払う。
「売上が一定額未満なら固定額、それ以上なら料率」という契約は、
最低保証と数学的に等価なので、後者として1つのルールに畳みました。

**税方式。** 2通りあります。

- `税込` … 支払額 = 税込売上 × 料率（料率の結果がそのまま税込）
- `税抜換算` … 支払額 = 税込売上 ÷ 1.08（軽減税率で税抜化）× 料率 × 1.1（手数料に課税）

商品は軽減税率8%、手数料は標準税率10%なので、ここを取り違えると金額がずれます。
端数処理の位置（合計で切り上げるのか、明細ごとか）も契約ごとに指定できるようにしました。

**稼働日数。** 日額方式は稼働日ごとの計上です。定休曜日はカレンダーマスタで除外し、
イレギュラー（臨時の稼働・休止、臨時の控除など）は月次調整シートで加減します。
調整のやり方は月ごとに運用側の判断で変わるので、計算式にはせず、入力された日数・金額をそのまま当てます。

**卸売。** 号機を介さない卸値取引があり、号機IDの代わりに専用ID（`W1` など）を割り当てて
同じ集計に乗せています。卸の手数料は、号機の支払先の1社にまとめて請求します（サンプルでは1本）。

## データモデル

```
支払先, 対象ID, 方式, 料率, 日額, 月額固定, 最低保証, 税方式, 備考
```

対象IDは号機ID（または卸売ID）です。**支払先名ではなくIDで結合する**ことで、
支払先の商号変更や機器の改名で数式が壊れないようにしています。

請求書番号に使う支払先コードは、並び順から独立させてあります。
支払先が増えても既存の請求書番号が動きません。

## 検証が見るもの

`verify_workbook.py` は請求額を Python 側で**シートとは独立に再計算**し、突き合わせます。
Excel数式のバグを検出するのが本命です。

そのほか発行前チェックとして:

- 発行日・登録番号・振込先の未記入
- 0円の請求書（条件設定漏れの兆候）
- 条件未確定の契約
- マスタ未登録の号機（**足し忘れると売上がどの集計にも乗らず静かに消える**）
- 発行台帳との食い違い
- 請求書シートの無い支払先

## 実運用で効いた判断

**料率や税方式を後から直すと過去月も変わります。** 発行済みPDFと食い違えば検証が検出します。
「発行済みは動かさない、直すなら次月から」という運用ルールとセットにしないと、
数式だけ直して過去の請求書と不整合になります。移行先のスプレッドシートでは、契約の行に適用期間を持たせ、
承認済みの台帳行と金額が食い違えばジョブが止まるようにしています。

**除外契約を明示的に残す。** 「この組み合わせは対象外」という判断は、
コメントとして契約マスタの隣に書いてあります。書いておかないと、
半年後に「なぜこの1台だけ請求されていないのか」を毎回調べ直すことになります。
