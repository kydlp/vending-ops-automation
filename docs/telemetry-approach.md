# 収集方式の設計判断

> ベンダー製品名、クライアントの構成、通信方式、呼び出し順は伏せています。
> ここに書くのは「同じ状況に置かれたときどう考えるか」であって、特定製品の攻略手順ではありません。

## 状況

販売管理システムは SaaS ですが、**外部連携用の公開APIがありません**。
運営側が自分の売上データを機械的に取り出す手段が、公式には用意されていない状態です。

公式クライアントはPCにインストールして使うアプリで、サーバとの通信は独自の形式でした。
汎用のHTTPクライアントで叩いても意味のあるものは返らず、リクエストを手で組み立てるのも現実的ではありません。

## 検討した3案

### 案1: RPA（画面操作の自動化）

アプリを起動して座標をクリックし、画面を読む。

却下しました。画面レイアウトが変われば壊れますし、実行中はマシンを占有します。
無人で定時に動かす前提だと、失敗時に何が起きたのか追えないのも困ります。

### 案2: 通信の再現

通信をキャプチャして、同じ内容を送る。

却下しました。独自形式のペイロードを手で組み立てることになり、
サーバ側のバージョンが上がれば黙って壊れます。

### 案3: 公式クライアントのライブラリを使う（採用）

**ベンダーの許可を得て、公式クライアントのライブラリ経由で取得する。**
公式クライアントと同じ手順でログイン・データ取得を行い、画面だけ出さない、という発想です。

採った理由:

- **公式クライアントと同じ経路を通る。** 通信の形式はライブラリが面倒を見る
- サーバ側の仕様が変わっても、ベンダーがクライアントを更新すれば、ライブラリを入れ替えて追従できる
- 画面に依存しないので、レイアウト変更では壊れない
- 取り込んだ売上を、検証月に旧ファイルの貼付データ・別途取得した月次値とそれぞれ突き合わせ、1円単位で一致することを確かめた

## 実装で効いたこと

**初期化を省略しない。** 公式クライアントは画面を出す前に初期化をしており、
そこを飛ばすと後続の呼び出しが意味のないエラーで落ちます。UIを使わないからといって
初期化まで飛ばしてよいわけではなく、「画面を描かない」だけにするのが正解でした。

**ログインで得た情報を後続の呼び出しに渡す。** 認証が通っただけでは不十分で、
ログインの応答に含まれる情報を、後続の呼び出しに引き継ぐ必要がありました。
ここを忘れると、**エラーにならず0件が返る**という一番たちの悪い壊れ方をします。
「0件」を正常系として扱わない検証を入れてあります。

**結果の有無は件数で判断する。** 「データあり」を示す表示が当てにならないケースがあり、
実際に返ってきた件数で判断しています。

**設定はファイル、秘密はコードに置かない。** 接続先・認証情報・通知先は設定ファイルへ。
リポジトリにはサンプルだけを置き、実値を含むファイルは追跡しません。

## 運用

- 請求に使う売上は、月次の `ingest` が前月分を1回で取る（毎月2日 06:00 の定時実行）
- これとは別に、毎晩1回（20時台）、号機ごとの補充後の販売本数を取ってチャットに通知している
- どちらもタスクスケジューラから起動する。常駐プロセスなし
- 実行ログは日付別ファイルにUTF-8で出す
- サーバが応答しないと接続待ちが長く続いたことがあり、1回の試行に時間の上限を設けた。
  上限を超えたら打ち切って時間をおいて1回だけやり直し、それでも失敗したら0以外の終了コードで終わる。
  タスク側の「失敗時に再実行」がそれを拾う
- 失敗したら通知チャンネルへ流す。**黙って止まらないこと**を最優先にした

## 法務・倫理面

- 運営側は**自社の売上データ**を取り出しているだけで、他社データには触れていません
- 参照だけで、サーバへの書き込みはしません
- 取得についてはベンダー担当者の了承を得ています
- 本リポジトリには**ベンダーのバイナリを一切含みません**。製品固有の識別子も伏せています
- 頻度は毎晩1回の通知と月1回の売上取得で、高頻度ポーリングはしていません
