# vending-ops-automation

自動販売機8台を運営する小売事業者の**月次バックオフィス業務を自動化した、実案件の記録**です。
公開にあたって匿名化しており、取引先名・設置場所・金額・単価などの数値はすべて架空の値に差し替えています（[匿名化について](#匿名化について)）。

## 30秒でわかる概要

| | |
|---|---|
| **課題** | 売上の集計から取引先10社ぶんの請求書・支払明細づくりまで、月次締めを手作業で回していた。旧Excelには計算ミスも埋もれていた |
| **やったこと** | 公開APIのない販売管理システムから売上を取り込み、契約条件をマスタ化したExcelブックで計算し、**検証を通ったときだけ**請求書PDFを出す仕組みを作った |
| **成果** | 月次締めが `monthly_run.py` のサブコマンド数本と人の確認になった。売上の取り込みは毎月定時に自動実行し、確認とドラフト作成は人が中身を見ながら流す |
| **いま** | Excel をやめて Google スプレッドシートを正本にする移行の途中。2026-11分を並行運用で照合し、2026-12分から切り替える予定（[移行中のこと](#移行中のことexcel--スプレッドシート)） |
| **技術** | Python（openpyxl）／C#／LibreOffice（ヘッドレスで再計算・PDF化）／Google Sheets API（サービスアカウント）／Windows タスクスケジューラ／Webhook通知 |

```bash
python monthly_run.py ingest       2026-09   # 前月分の売上を取り込む（毎月2日 06:00 に定時実行）
python monthly_run.py import-other 2026-09   # 入力用スプシの「その他売上」を取り込む（手動）
python monthly_run.py remind       2026-09   # 請求額を通知して確認を促す（現在は手動実行。定時実行への切り替えを予定）
python monthly_run.py draft        2026-09   # 検証を通してから請求書PDFを出す（手動）
```

この公開版に入っているのは `ingest` / `remind` / `draft` と検証・PDF化です。`import-other` と、移行先のスプレッドシート用ジョブは含めていません。

## 課題

- 販売管理システム（以下VMS）の画面から売上を手で写し、Excelに貼り付けていた
- 自販機ごとに設置場所のオーナーが違い、**契約条件が1社ずつ違う**（売上×料率、回収現金から日額×稼働日と月額固定を差し引く現金渡し、最低保証、税込／税抜換算など）
- 旧Excelは取引先ごとに11枚のシートがあり、セルの直接参照と数式への単価直書きで成り立っていた。調べると、`#REF!` で計算が成立していないシート、1行ズレた参照による二重計上、値上げした月から壊れる数式が見つかった

## 設計の考え方

### 1. 公開APIのないシステムから、画面操作に頼らず取得する

VMSには外部連携用の公開APIがありません。**ベンダーの許可を得て、公式クライアントのライブラリ経由で取得**しています。

| 選択肢 | 判断 |
|---|---|
| RPA（画面操作） | 画面レイアウトが変わると壊れる。実行中はマシンを占有する → 不採用 |
| 通信の再現 | 通信内容を手で組み立てるのは現実的でなく、サーバ側の更新で黙って壊れる → 不採用 |
| **公式クライアントのライブラリを使う** | **採用。** 公式クライアントと同じ手順でログイン・取得を行い、画面だけ出さない。通信の中身はライブラリが面倒を見る |

取り込んだ売上は、検証月に旧ファイルの貼付データ・別途取得した月次値とそれぞれ1円単位で一致することを確かめています。詳しくは [docs/telemetry-approach.md](docs/telemetry-approach.md)。

### 2. VMSの実績を唯一の正にする

手入力とVMSの二重管理をやめ、自販機の売上の数字はVMSの実績だけを使います。旧Excelでは手入力とVMSの月合計が一部の号機でズレていましたが、この設計ではズレが構造的に起きません。

- 単価と契約条件はマスタに外出しし、値上げや料率変更はマスタの1行を直すだけにした（単価は履歴で持つ）
- すべての数式を**号機名ではなく号機IDで結合**。システム側で機器名が変わっても壊れない
- 数式はGoogleスプレッドシートにもある関数に限定し、`verify_workbook.py` で確かめる。ただし**正本のxlsxをスプレッドシートで開いて保存するのは禁止**（過去に型・保護・数式が壊れた）
- 取引先が増えても、ブックを作り直さずマスタに1行足すだけ

### 3. 旧ファイルの金額を1件ずつ再現してから移行する

新しいブックの計算結果を、旧ファイルの金額と1件ずつ突き合わせました。一致しない箇所は旧ファイル側の不具合（行ズレ、`#REF!`、ベタ打ちの上書きなど）として原因を特定し、記録したうえで移行しています。

### 4. 請求書は「検証を通ったときだけ」出す

お金が動くので、出す前に止める仕組みを先に作りました。`verify_workbook.py` が請求額を**Python側でシートとは独立に再計算**し、シートの値と突き合わせます。

- 数式のスプレッドシート互換性、再計算後のエラーセル
- Pythonによる再計算との差（シートの数式バグを見つける本命）
- 発行日・登録番号・振込先の未記入、0円の請求書、条件未確定の契約
- マスタ未登録の号機（足し忘れると売上が**どの集計にも乗らず静かに消える**）
- 発行済み台帳との食い違い、請求書シートの無い支払先

ひとつでも引っかかれば終了コード1を返し、`draft` はPDFを出さずに通知して止まります。出力はあくまでドラフトで、**発行は人が確認して承認してから**です。自動化したのは作業で、承認ではありません。

### 5. 人が入れる売上は入力用スプレッドシートから読む

EC・催事・卸など、VMSに載らない売上は人が入力用のGoogleスプレッドシートに入れます。`import-other` がそれを**閲覧専用のサービスアカウントで** Sheets API から読み、正本の `入力_その他売上` の対象月の行だけを置き換えます。

- 書き込む前に正本の写しを残す
- 入力用スプシに対象月の行が無ければ、既存行を消さずに止まる（本当に空にするときだけ `--allow-empty`）
- `--dry-run` で書かずに中身だけ確かめられる
- 対象IDを付けた行だけが手数料の計算に乗り、付けない行は売上の記録として残るだけ

## 成果

- 月次締めが `monthly_run.py` のサブコマンドと人の確認・承認になった
- 取引先10社ぶんの請求書・支払明細PDFを、算定根拠の明細つきで出力
- 定時実行に載っているのは売上の取り込み（`ingest`、毎月2日）だけ。金額の確認（`remind`）は現在は手動実行で、定時実行への切り替えを予定している。ドラフト作成（`draft`）は人が手で流し、中身を見て承認する
- 旧Excelに埋もれていた計算ミス（行ズレによる二重計上、`#REF!`、ベタ打ちの上書き）を特定して直した

## 移行中のこと（Excel → スプレッドシート）

2026-11 時点で、正本をExcelからGoogleスプレッドシートへ移す作業を進めています。**まだ切り替えていません。**

- スプレッドシートを正本にし、計算・請求書PDF・発行台帳はPythonの月次ジョブが作る（請求書のシートはスプレッドシートに持たない）
- ジョブが書く範囲はロックし、人が入れてよいセルだけを開ける（保護と入力規則をジョブが付け直す）
- 承認済み・発行済みの台帳行は番号と金額を固定し、あとで計算が変わるとジョブが止まる
- 2026-11-08 のリハーサルで、過去15か月分を入れた本番用スプレッドシートの請求額・請求書の中身がExcelと10社とも一致した
- **2026-11分はExcelとスプレッドシートの両方で回して照合し、2026-12分から切り替える予定**。切替の前に決めることがまだ残っている

## 動かしてみる（合成データ）

Python 3 と LibreOffice が必要です。

```bash
pip install openpyxl
cd billing
python prepare_sample.py                               # 合成データを夜間・回収時の2本に分ける
python build_workbook.py 2026-06                       # ブック sales-ledger.xlsx を作る
python verify_workbook.py sales-ledger.xlsx 2026-06    # 発行前検証
python export_invoices.py sales-ledger.xlsx invoices 2026-06   # 請求書PDFを出す
```

合成データの回収時の各行は、前回の回収日から回収日の前日までの夜間の合計です。そのため号機×月の合計は夜間とほぼ同じで、差は月末時点で未回収の分と前月からの持ち越し分だけです（`prepare_sample.py` が表で出します）。

サンプルのブックには発行日（2026-07-05）を入れてあるので、検証は「判定: OK」になり、請求書PDFにも発行日が出ます。
LibreOffice が既定の場所（Windows の `C:\Program Files\LibreOffice`）にない場合は、環境変数 `SOFFICE` に `soffice` のパスを指定してください。
売上の取得（`monthly_run.py ingest`）はベンダー製品への接続が必要なため、このリポジトリだけでは動きません。

## 匿名化について

実案件の記録なので、公開にあたって以下を差し替えています。

- 取引先名 → `ClientA`〜`ClientK`、設置場所 → `SiteA`〜`SiteH`、商品名・発行者名 → `OurProduct`・`OurCompany`
- 売上・単価・料率・固定額・最低保証額・卸値・満タン本数・定休曜日 → **契約方式の多様性は保ったまま、数値は架空の値**
- 住所・電話番号・振込先・登録番号 → `〒000-0000`、`000-0000-0000` などのダミー値
- 事業者登録番号、端末シリアル、担当者名、認証情報、Webhook URL、ストレージパス
- ベンダー製品名とそのバイナリ、製品固有の内部識別子・画面ID・通信方式
- 補充・回収の体制やシフトなど、現場の運用の細部

コードの構造・アルゴリズム・検証ロジックは実物（Excel正本の運用時点）に沿っています。
